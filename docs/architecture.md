# Architecture

## Request paths

The FastAPI application has exactly two outbound AI-related routes:

| Purpose | Gateway route | Authentication |
| --- | --- | --- |
| Chat completions | `/default/models/openai/v1/` | Explicit lowercase `api-key` runtime key header |
| MCP tools | `/default/toolservers/appservice-ops/mcp` | Explicit lowercase `api-key` runtime key header |

`Settings` rejects any OpenAI base URL that does not end in the first route
and any MCP URL that does not end in the second. There is no provider endpoint
setting, credential setting, or fallback path in the application.

`GatewayAgent` builds an `openai.AsyncOpenAI` transport against the OpenAI v1
gateway route with the explicit `api-key` header, an `httpx.Timeout` from
application settings, and `max_retries=0`. It passes that transport to
`OpenAIChatCompletionClient` and closes it when the connected agent closes.
The application retry wrapper is therefore the sole model retry mechanism.
It builds an `MCPStreamableHTTPTool` for the gateway ToolServer route with:

- a 30-second explicit MCP request timeout;
- a fixed gateway-published `appservice-ops_get_service_status` and
  `appservice-ops_get_deployment_context` allow-list;
- an origin-scoped header provider for the runtime `api-key`.

The ToolServer then adds `x-appservice-mcp-secret` to its backend request. The
FastAPI `/mcp` endpoint rejects absent or invalid values in constant time. It
does not expose mutable or destructive tools.

## Streaming and errors

`POST /api/chat/stream` emits SSE events:

| Event | Meaning |
| --- | --- |
| `meta` | Generated or caller-supplied correlation ID |
| `delta` | A model text fragment |
| `error` | Sanitized gateway failure code and safe message |
| `done` | Stream completion |

The retry wrapper has a maximum of three attempts by default:

- HTTP 401 and 404 are never retried.
- HTTP 429 retries only before a first streamed chunk. It uses a bounded delay
  and honors `Retry-After` when present.
- Transient 5xx failures retry only before a first streamed chunk using
  bounded exponential backoff plus jitter.
- Any failure after a partial stream ends the stream without replaying output.

Response bodies, prompts, and exception text are not propagated to logs or
SSE errors.

## Azure resources

`infra/main.bicep` is subscription scoped. It creates a deterministic
environment resource group and invokes the resource-group workload module.
The module creates:

- Linux Premium v3 App Service plan at P0v3, capacity 1, web app, and staging
  slot.
- VNet plus a delegated App Service integration subnet. A Key Vault private
  endpoint and private DNS are opt-in because the portable default uses public
  Key Vault access; a private endpoint is available where the network design
  supports it.
- RBAC-enabled Key Vault. The supplied deployment principal receives Key Vault
  Secrets Officer for post-provision data-plane writes, while the app and its
  staging slot receive only Key Vault Secrets User. No secret values appear in
  Bicep outputs.
- Log Analytics and workspace-based Application Insights.
- Azure AI Services and a parameterized `gpt-5-mini` GlobalStandard capacity-1
  deployment named `appservice-chat`, with a 1000 TPM default structured
  policy.
- Dedicated AI Gateway, connector namespace, existing default workspace,
  Foundry model provider, stable model registration, runtime API key,
  ToolServer, structured token policy, and telemetry exporter.

The dedicated gateway uses a system-assigned identity. Bicep grants it Foundry
User (`53ca6127-db72-4b80-b1b0-d745d6d5456d`) at the Azure AI Services scope.
The Foundry provider uses managed identity with resource
`https://cognitiveservices.azure.com/`.

The Foundry deployment and gateway model ARM resource both use the stable
client alias `appservice-chat`; the gateway `displayName` and deployment
catalog model remain `gpt-5-mini`. A backing model/version swap therefore keeps
the deployment and client-visible name stable, matching the published pattern.

The plan and production app add `azd-service-name: web` to the shared
environment tags; the staging slot intentionally does not compete for azd
service discovery. Predeploy explicitly sets azd's
`AZD_DEPLOY_WEB_SLOT_NAME=production` target. Postdeploy verifies production
directly and never swaps the staging slot automatically. Staging is an
optional/manual deployment-slot demonstration that must be explicitly deployed
and health-checked before a separate swap. Before `azd down`, the bounded
`predown` lifecycle hook
records a verified current-environment gateway marker; `postdown` may purge
only the matching soft-deleted gateway.

## Secrets and deployment flow

The gateway runtime key is generated by the gateway resource. After
provisioning, the hook uses the `listSecrets` action, writes that value to Key
Vault, generates a separate MCP backend secret, and PUTs the ToolServer
credential payload. App Service consumes both values through Key Vault
references.

The Bicep module follows the Microsoft baseline's secure `toolServerConfigs`
pattern with an empty default rather than creating a credential-less
ToolServer. Post-provision owns the first ToolServer PUT and supplies the
verified streamable HTTP/header credentials payload only after generating the
backend secret.

The hook uses short-lived, owner-only files inside the active `.azure`
environment directory so it can pass secret material to Azure CLI without
placing it in terminal output, azd environment values, or command logs. It
removes those files on exit.

Secret creation uses the Key Vault ARM resource API rather than requiring the
deploying workstation to reach the vault data plane. This supports the Demo
Three `SecuredByPerimeter` setting; App Service reaches the vault privately
through its VNet integration, Key Vault private endpoint, and private DNS.

Before provisioning, an initialization hook supplies portable defaults for
optional azd parameters and resolves the current deployment principal when
`AZURE_PRINCIPAL_ID` was not explicitly set. This prevents empty string
substitutions from overriding Bicep defaults.

## Observability

The application configures Azure Monitor OpenTelemetry when
`APPLICATIONINSIGHTS_CONNECTION_STRING` is supplied. It accepts only this
allow-list of custom attributes:

- `correlation_id`
- `http.route`
- `http.response.status_code`
- `gateway.status_code`
- `gateway.error_code`
- `service.name`

Prompts, model responses, runtime keys, MCP backend secrets, and upstream
response bodies cannot be added by the helper. Correlation IDs are returned
in `X-Correlation-Id` and forwarded to model calls.

The gateway OTLP telemetry exporter is preview behavior: it exports model
token usage only and does **not** export MCP traffic.

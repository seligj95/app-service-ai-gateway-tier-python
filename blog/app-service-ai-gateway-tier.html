What the New API Management AI Gateway Tier Changes for App Service-Hosted Agents

The primary contribution here is a small, runnable App Service sample: a Python FastAPI chat application, a read-only MCP endpoint, Microsoft Agent Framework integration, azd+Bicep infrastructure, and tests. It is a preview-only learning sample with no SLA, not a production-ready claim.

Three related, but different, gateway experiences

Experience What it provides What this sample uses
Regular API Management AI gateway capabilities AI-aware policies, model routing, token controls, observability, and MCP-oriented patterns on a regular APIM service. No. The sample does not use regular APIM XML policies or a regular APIM SKU.
Foundry-created or associated regular APIM A Foundry workflow can create or associate a regular APIM surface and its management experience. No. It is a separate provisioning and management path from the dedicated tier shown here.
Dedicated API Management AI Gateway tier A focused AI Gateway resource with a default workspace, provider/model catalog, runtime keys, ToolServers, structured policies, and telemetry exporter. Yes. The application uses the dedicated gateway's OpenAI v1 model and ToolServer routes exclusively.

Why the dedicated tier matters to an App Service agent

Instead of binding the application to a provider deployment name, the agent calls a stable catalog model named appservice-chat at the gateway OpenAI v1 route. The backing Foundry deployment can be evaluated separately from application configuration. Stable model swap behavior remains a preview item to verify before making an operational claim.

The sample also uses a gateway ToolServer. The Agent Framework MCPStreamableHTTPTool reaches the dedicated route for appservice-ops with the gateway runtime key. The ToolServer adds a different backend header before reaching FastAPI. That means a direct call to the App Service MCP endpoint is denied without the backend secret.

What to look for in the portal and APIs

  • A dedicated gateway card and its default workspace.
  • A Foundry provider with the appservice-chat model catalog entry.
  • The runtime key resource used by the application through Key Vault rather than application settings in source.
  • The ToolServer entry for the read-only App Service MCP server.
  • Card and JSON policy experiences, including the structured token-limit policy array rather than XML policy text.
  • Multiple provider and model catalog possibilities, plus a self-service catalog experience where the preview exposes one.
  • An Application Insights telemetry exporter and the distinction between application telemetry and gateway token usage.

Gateway OTLP telemetry is preview behavior. In this sample it is documented as model token usage only, not MCP traffic.

Walkthrough of the sample

  1. Deploy the azd+Bicep environment in an entitled preview region.
  2. Allow the bounded post-provision hook to retrieve the gateway-generated runtime key, store it and a generated MCP backend secret in Key Vault, and update the ToolServer credential payload.
  3. Open the App Service chat page. Its SSE endpoint creates a correlation ID and streams model text through the dedicated OpenAI v1 route.
  4. Ask an operational question. The Agent Framework can use the read-only MCP ToolServer route; the gateway injects the backend secret only on that hop.
  5. Use the documented failure procedures to confirm 401, 404, token-policy 429 behavior, mocked 5xx retry behavior, direct MCP denial, and telemetry boundaries. Because preview 429 responses may omit Retry-After, the client uses bounded fallback backoff when the header is absent.

Preview cautions

The dedicated tier is preview-only with no SLA. Regional availability, pricing, numeric limits, portal naming, policy behavior, and API contracts can change. Validate the experience in the selected subscription before presenting screenshots or making capability claims.
